# 从成功轨迹提取参数化操作片段

日期：2026-10-19。范围：原始论文方法对照、当前项目记录格式审阅和最小方案设计。本文没有实现提取器，没有新增手机操作，也没有验证任何新技能的成功率。

**同日补充核查与更正：**首轮遗漏了直接的手机端近邻 [SkillDroid: Compile Once, Reuse Forever，2604.14872v1](https://arxiv.org/html/2604.14872v1)，提交于 2026-04-16。其 §3.2.3 已将成功手机操作轨迹编译为带类型槽位和元素定位器的技能，§3.3–3.4 包含复用、单步回退和重新编译。因而不能将“把成功轨迹提取为参数化技能并在安卓复用”作为平台迁移层面的新贡献。本文方案须以它为直接基线重新比较，初版文献覆盖不完整。

## 1. 研究结论

建议采用“执行记录标准化 → 有依据的片段切分 → 参数来源与用途标注 → 当前页面目标描述 → 候选生成 → 变参验证”的流程。

核心产物不是一份把人名替换成花括号的操作日志，而是一个带入口条件、输入参数、步骤、退出证据和适用范围的短流程。

一次成功足以提出候选，不能证明泛化。第一版以同一 App 中的短直线流程为范围，优先支持任务明确给出的文本和目标名称。跨 App 迁移、复杂循环、隐式日期和动态读取值先列为后续扩展。

参数化提取本身已有成熟先验工作，不能作为“首次”贡献。最需要研究的是参数角色与来源能否正确绑定，以及这种绑定能否减少换参数之后的误操作。

## 2. 已有方法具体做到哪一步

### SkillDroid：直接的安卓参数化技能近邻

[SkillDroid](https://arxiv.org/html/2604.14872v1) §3 已覆盖本方案相当一部分流程，应优先于仅有浏览器背景的方法进行比较。其 §7 明确说明当前感知依赖 A11Y 文本，技能限于单 App 单任务；这些限制只代表该版本的范围，不代表视觉技能或跨 App 技能在整个领域无人研究。来源绑定、多实例约束等拟议差异仍需逐项核对并实验验证，不能由本文的设计描述直接认定原创。

### AWM：从具体经验抽象出可复用子过程

[Agent Workflow Memory](https://arxiv.org/html/2409.07429v1) §2.2–2.3 使用语言模型从经验中提炼较细粒度的子任务，并将示例特有的值替换为占位符。流程主要作为后续模型的记忆指导。

可借鉴“先切子过程再抽象值”。不能把仅保存文字步骤当作已经实现直接执行。

### SkillWeaver：成功轨迹合成为函数，再用新参数测试

[SkillWeaver](https://arxiv.org/html/2504.07079v1) §2.2–2.3 将状态动作记录交给模型生成 Python API，包含签名、文档和前提说明，并进行静态检查与参数化测试。

可借鉴候选生成和测试分离。其浏览器函数依赖 Playwright，不能直接移植成安卓中永久有效的坐标脚本。

### WebXSkill：短片段、类型参数和步骤说明

[WebXSkill](https://arxiv.org/html/2604.13318v1) §3.1 与附录 A.1.3 从轨迹中发现连贯子序列，将具体动作值抽象成类型参数，并保存每步目标和说明；同时做去重和环境执行验证。

这是本研究最直接的流程近邻。它已经覆盖“轨迹提取成带参数片段”，不能仅将 JSON 换成安卓版本就声称原创。

### DeltaReplay：区分可直接复用与必须替换的参数

[DeltaReplay](https://arxiv.org/html/2610.11707v1) §4.4 根据规则识别旧任务参数，并对齐新旧指令来替换输入文字和点击目标；映射不明确时回退基础智能体。它执行的是当前屏幕目标，而不是旧编号。

可借鉴不明确时放弃复用。其 §6 指出，逐词对齐难以处理“明天”这类隐含值。这为参数来源和显式变换提供了具体的比较点，但不证明我们拟议方案一定优于它。

### EAM 与 TeleTune：提供两种补充视角

[Executable Agentic Memory](https://arxiv.org/html/2605.12294v1) §4.1 用高频相邻动作合并来挖掘动作组。适合样本较多时发现重复结构；高频本身不保证有独立语义或能变参。

[TeleTune](https://arxiv.org/html/2610.05437v1) §2 在固定日志上优化文字技能库，用保留集的动作预测进展选择更新。可用作低成本离线筛查的参考，但在旧日志上预测正确，不等于新参数下能完成闭环任务。

本次对照限定于上述实际阅读的版本和方法段落。没有复现其代码或核验所有报告数字，也不声称已经穷尽参数化技能学习文献。

## 3. 当前项目的数据够不够

### 已经有的记录

`agent.py::trace` 保存任务、状态、历史、模型调用和事件。`_execute` 中的历史记录包含实际动作、输入文字、动作模式、执行错误、前后页面指纹和摘要。页面摘要引用截图文件；录制启用时 `_record_page` 保存图像。

CLI 会通过 `record_dir` 或任务运行目录保存 trace。直接使用 Python Agent 时，录制是否启用取决于调用参数。

这些数据可以形成离线候选：

| 数据 | 可以支持什么 |
|---|---|
| 用户原任务 | 提出候选参数，例如收件人和消息内容 |
| `device_action` 与 `text` | 确认实际执行了什么以及实际输入了什么 |
| 前后页面摘要和截图 | 判断局部目标是否达成，提出片段边界 |
| 模式与错误 | 区分正常步骤、恢复过程和待解释的失败 |
| 最终任务状态与复核 | 筛选候选任务，但仍需评价证据质量 |

`success=True` 表示动作执行没有抛出记录中的错误，不表示业务目标已实现。`page_changed=True` 表示观察变化，不表示任务前进。不能直接以这两个字段作为学习标签。

### 需要补充或明确的数据

1. 每步观察和动作之间的稳定引用，关联动作前后对应的控件快照与截图。
2. 被操作控件的资源 ID、原始文本、描述、角色和必要的父容器上下文。当前 `a11y.py` 能读到资源 ID，但构造动作时主要保留标签、角色、节点编号和几何信息，不能从已有 `device_action` 假定取回完整定位信息。
3. 输入值的来源。例如来自任务原文、任务日期换算、前一步页面读取，还是模型临时生成。
4. 每项参数具体用于哪些输入、选择目标和结果判定。
5. 本地证据结论及证据不足状态，区别于执行器预期效果和自述。
6. App 版本、语言和账户环境等适用性信息，在需要时用于限制复用范围。

`vision.page_summary` 的页面文字目前截断到 1500 字符，不包含完整逐步控件树。旧日志不能凭空补回已丢失的字段。可以尝试从已有截图生成低置信度候选，但不要伪造资源 ID 或完整层级。

## 4. 片段应该长什么样

用用户提供过的 QQ 任务作为说明，以下均为拟议表示，不代表已经生成可执行技能。

原任务：“打开 QQ 给王鑫说你好。”某条成功路径可能是：

```text
桌面 → 打开 QQ → 点击王鑫会话 → 输入你好 → 点击发送
```

第一版建议提出两个候选，而不是把全部动作锁死成一条脚本：

```text
候选一：打开 QQ
入口：QQ 未在目标前台状态
出口：QQ 的受支持入口页可见

候选二：从 QQ 会话列表向可见联系人发送文字
参数：recipient 和 message
入口：会话列表可见，目标可唯一识别，受支持输入框可用
过程：进入目标会话 → 输入 message → 发送
出口：目标会话出现本次新增的己方 message
```

这里没有学到“联系人不在列表时搜索”“选择多个同名联系人”或“首次登录”。这些情况应当超出该候选范围，由现有智能体处理。以后获得新的成功路径，再考虑扩展。

## 5. 提取流程

### 第一步：选择有可信结果的轨迹，并保留证据不确定性

先选择结果已被合理观察支持的任务。受控研究中优先使用独立评测器，人工审阅可作为小规模先导的标签来源。现有复核器可提供候选成功判断，但它自身有误差。

最终任务成功并不意味着每一步都必要。恢复前的误点、无效等待和弹窗处理可以单独标注，不应整条照收。

也不能把 `changed=False` 的动作直接删除：输入框聚焦或后台提交可能没有显著全屏变化。剪除步骤会改变因果链，必须通过后续重放或其他证据验证。

### 第二步：按可观察的局部结果切分

推荐使用“页面入口与局部目标达成”作为主要边界，动作类型和页面变化作为候选线索。

例如：

| 片段 | 入口 | 出口 |
|---|---|---|
| 打开会话 | 会话列表 | 目标标题和聊天输入区域可见 |
| 填入消息 | 目标聊天页和受支持草稿状态 | 输入框等于指定内容 |
| 发送已确认草稿 | 草稿等于指定内容 | 本次新增消息证据出现 |

前两项也可以与第三项合并成一个短技能。不是越短越好：只有“点击一个按钮”几乎没有复用收益；整段十几步又容易把偶发弹窗和恢复过程混在一起。

先从约 2–6 个业务动作的直线片段试验，长度只作工程初值。更重要的是入口可识别、局部效果连贯、参数依赖完整和具有重复使用机会。

第一条轨迹可以让 LLM 提议边界，边界必须引用真实动作位置和前后观察，不允许生成未发生的操作。收集多条后，再按语义状态与动作骨架对齐，并用重复子序列辅助去重。

### 第三步：区分变量与常量，追踪来源和用途

对 QQ 示例可作如下分类：

| 轨迹中的值 | 拟议分类 | 使用方式 |
|---|---|---|
| 王鑫 | 用户任务输入 `recipient` | 会话选择与聊天身份判定 |
| 你好 | 用户任务输入 `message` | 实际输入与新增结果判定 |
| 发送 | 固定界面语义 | 发送控件定位，不作为消息参数 |
| QQ 包名 | 当前技能适用范围 | 第一版固定，不自动扩展为任意 App |
| 14:02 或通知角标 | 观察中的临时值 | 不能直接当作未来成功条件 |
| index 20 与旧坐标 | 本次观察的临时引用 | 不进入可跨运行复用的目标定义 |
| 从页面读出的会议时间 | 运行时观察绑定 | 每次重新读取，不能固化旧值 |

对每个变量记录来源、类型、示例值、生产它的步骤，以及使用它的动作或断言。

特别要防止两个错误：

- 同一个示例字符串被用于不同语义角色。例如“给你好发送你好”，收件人和消息值相同，仍应是两个独立参数，不能全局替换成同一个变量。
- 任务隐含的变换被抹掉。例如“设明天早上八点的提醒”包含日期求值，不能把当次日期直接写成参数默认值。若支持它，应记录相对哪个日期与时区求值；第一版可以直接不支持。

类型只能排除部分错误，联系人和消息都是字符串时仍可能交换。必须同时保留角色和使用位置。任务要求的精确输入内容应原样保留，不能为了匹配而任意清理空格、标点或换行。

### 第四步：把旧控件引用转成当前页面可求解的目标

不能保存 `CLICK(20)` 并在下次沿用。它只能证明该次点击的编号是 20。

拟议目标描述应表达：在 QQ 的会话列表里，找到表示 `recipient` 的会话行；进入后，在该会话的聊天区域找到消息输入框和发送控件。

优先利用有证据的资源 ID、角色、可见文字和父容器关系。任何单个属性都可能变化或歧义，资源 ID 也不保证唯一。对于“王鑫, 你好, 昨天……”这样的整行标签，应定位联系人标题或行内关系，不能要求整串动态预览永远相同。

当前运行中匹配唯一且合适的目标，再获得这次的编号或坐标。目标缺失或同名歧义则停止该技能并返回原智能体，不按旧位置猜。

视觉坐标步骤没有足够语义证据时，只能保存为“需要重新视觉定位”的步骤，不能声称已编译成确定性快动作。第一版可只提取定位证据较好的 A11Y 片段。

这一步使用正常动作后观察得到的当前状态即可设计，本文不提出修改用户既定的 fast 模式执行前核对行为。

### 第五步：保存结构化候选，而非执行任意生成代码

第一版适合一个固定解释器可以理解的声明式格式。下面的 JSON 是设计示例，字段与判定函数尚不存在于当前项目：

```json
{
  "name": "send_text_from_visible_conversation",
  "app": "com.tencent.mobileqq",
  "status": "candidate",
  "parameters": {
    "recipient": {"type": "contact_query", "source": "task"},
    "message": {"type": "text", "source": "task", "preserve_exact": true}
  },
  "entry": "conversation_list_with_unique_recipient",
  "steps": [
    {"op": "click", "target": {"kind": "conversation", "name_param": "recipient"}},
    {"op": "fill", "target": {"kind": "message_input"}, "value_param": "message"},
    {"op": "click", "target": {"kind": "send_button"}}
  ],
  "exit": {
    "kind": "new_outgoing_message",
    "conversation_param": "recipient",
    "content_param": "message"
  },
  "evidence": {"run_id": "source_run", "steps": [2, 3, 4]}
}
```

真实候选还应附上受支持的草稿状态、目标描述证据、App 环境和验证记录。示例用语义类型帮助阅读，不表示只写一个 `kind` 就能定位安卓控件。

不同角色的字符串通过参数引用绑定，不使用简单全局字符串替换；将来映射到底层定位或输入时按数据处理，避免把参数意外解释成表达式或选择器代码。

片段可以返回观察值或产生实体，但只有轨迹有相应证据时才能定义输出。读取值在片段外产生时，应作为显式导入；由片段内步骤读出时，应有绑定步骤。不要把源轨迹里看到的具体值伪装成普遍常量。

### 第六步：从候选到可复用能力

静态检查主要确认格式、动作支持、参数是否都有来源、引用位置是否合理、是否残留旧编号，以及有无不成立的输出声明。

然后在可重置测试环境中检查：

1. 用原参数复现，验证是否忠实提取。
2. 只替换一个参数，检查对应目标、输入和结果判定是否一同变化。
3. 替换多个参数，检查是否交叉绑定。
4. 候选目标不存在或有歧义时，检查是否正确停止复用。
5. 改变列表顺序、窗口尺寸或动态预览，检查是否依赖旧几何或动态标签。
6. 放入相似旧结果，检查是否误判本次任务完成。

没有经过这些运行验证的候选，可以作为低置信度提示，不应直接被标记为“任意参数都能执行”。验证通过也只覆盖已测试的参数类别和入口范围。

上述测试是研究方案，本轮没有向真实联系人发送任何测试消息。

## 6. LLM 与代码分别做什么

| 阶段 | LLM 的适用工作 | 代码与实际环境的责任 |
|---|---|---|
| 轨迹理解 | 提议局部目标和边界 | 保留实际动作顺序和证据引用 |
| 参数归纳 | 判断语义角色与候选来源 | 校验值、引用和使用位置，保存不确定性 |
| 目标抽象 | 提议稳定属性与上下文 | 当前观察中解析目标，不复用旧编号 |
| 结果归纳 | 提议可观察的效果 | 将预期效果和实际证据分开保存 |
| 泛化确认 | 生成值得测试的参数组合 | 执行受控验证与独立结果判断 |

可以在任务成功后异步或离线调用一次较强模型生成候选，控制上下文只包含相关轨迹、必要图片和已有技能摘要。不要为了提取技能，在正常执行每一步都新增一轮 LLM 请求。

仅做字符串扫描可以提出候选槽位，例如任务文本与实际输入相同；但无法可靠区分所有来源。LLM 同样不能凭一条轨迹确定参数化方案一定正确。二者都要通过不同实例约束。

## 7. 多条轨迹怎样帮助归纳

假设存在三条已验证的同结构路径：

```text
给王鑫发送你好
给李明发送收到
给王鑫发送下午三点见
```

不要直接按表面字符串做最长公共子序列。先对齐角色和状态：

```text
会话列表 → 选择 recipient → 目标会话
目标会话 → 输入 message → 草稿就绪
草稿就绪 → 提交 → 新消息可观察
```

不同实例的变化可以支持参数解释；保持不变的值仍不一定是常量，可能只是样本没有覆盖。某个参数只出现一个值时，应保存“推测可变，尚未验证”的状态。

只有一条轨迹遇到欢迎弹窗，不应把“关闭欢迎弹窗”作为所有运行必经步骤。可以将该次恢复独立保存；只有明确识别到弹窗时才尝试相应分支。第一版可以暂不把这种偶发恢复纳入主片段。

第一版也不必做全局最优片段挖掘。先用已有结果证据提出少量短候选，按入口、效果、动作骨架和参数角色去重即可。样本增长后，再比较 LLM 切分与频率挖掘的收益。

## 8. 怎样避免“又多了一套组件却没有提速”

需要区分两种复用方式：

- 指导式：给 Jev 当前局部目标与参数，每步仍由 Jev 从当前候选中选择。可以减少视觉推理，但 Jev 请求数不一定减少。
- 直接解析式：固定规则已能在当前观察中唯一解析目标时直接执行，否则回退 Jev 或视觉。更可能减少请求，但定位和适用性验证要求更高。

两者都不能凭旧坐标开环执行整段操作。也不必每步加一个新 LLM 验证器；可以使用已采集的当前观察和可计算条件，保留必要的业务结果复核。

技能编译与验证也有成本。若编译验证成本为 `C_build`，每次复用相对基线实际节省 `ΔC`，且 `ΔC > 0`，那么粗略需要超过 `C_build / ΔC` 次复用才摊平。时间与费用应分别核算，故障恢复和失败尝试也要计入。

已有日志显示设备观察也是主要耗时来源，因此减少模型请求并不等于总时间按同比例下降。提取研究要同时记录在线模型成本、设备成本和离线构建成本。

## 9. 最小研究实验

### 先导范围

先选择 3 类短流程，例如搜索内容、填写并保存条目、从列表进入目标详情。每类收集若干不同参数实例，先人工标注边界、参数角色、来源和目标证据。收集量根据歧义情况调整，不预先宣称几条轨迹足够证明泛化。

QQ 可以用于解释和后续有授权的真实任务评估；初期自动变参验证优先使用可重置测试 App，避免将不能回滚的真实消息行为当作数据生成环境。

### 对照方法

1. 无技能的当前系统。
2. 原轨迹作为示例提示。
3. AWM 风格的文字参数化子流程。
4. 一次 LLM 直接生成参数化结构，使用相同运行时。
5. 本文拟议的来源与用途标注，以及多实例约束和变参验证。

需要实现合理的 DeltaReplay 风格新旧参数对齐基线，检验显式参数来源是否提供额外收益。比较时用同一底层模型、观察接口、动作集合和预算。

### 指标

- 片段边界：与人工可接受切分的符合程度；允许多个合理边界。
- 槽位绑定：来源、角色和所有使用位置是否正确，特别记录收件人和正文交叉错误。
- 目标恢复：旧编号或排序改变后能否定位正确当前控件。
- 参数泛化：保留的新参数及组合下的闭环完成率。
- 不适用拒绝：未知入口、缺目标和同名歧义下是否拒绝错误复用，同时记录过度拒绝。
- 成本：全部尝试的在线耗时、模型请求、设备观察、构建验证费用与复用摊销。

训练和测试应按完整任务运行与参数组合划分。同一原轨迹派生的变体放在同一划分；另报告新界面或新版本场景。离线动作预测正确只作筛查指标，不能替代闭环成功。

### 能成为研究贡献的条件

“参数化片段”已不是新概念。候选差异在于：显式的参数来源和使用关系，能否在少量真实安卓轨迹中，比直接 LLM 总结或新旧指令替换更准确地完成变参复用。

如果优势只来自更多样本、更多模型调用或更好的目标解析，不能归功于提取方法。消融需要分别拿掉来源信息、多实例约束与变参验证，并保持其他部分一致。

若简单槽位替换基线已经同样有效，就应保留这个工程功能，但不把它单列为算法创新。若真正瓶颈是缺少可用的控件定位证据，应先完善记录，而不是继续增加提取器复杂度。

## 10. 推荐实施顺序

1. 明确逐步记录协议，先能回溯参数、目标和结果证据。
2. 从一条有证据支持的成功轨迹生成少量短候选，状态保持 candidate。
3. 第一版只支持用户明确给出的目标名称和精确输入文本，固定 App 和页面范围。
4. 静态校验后，在受控环境替换参数验证。
5. 再加入多条轨迹对齐和去重，记录实际复用收益。

不需要一开始引入向量数据库、复杂知识图谱、强化学习或任意代码生成。研究阶段的主要工作量在数据质量、语义绑定和验证设计。
