# QQ 视觉任务性能检查

检查对象：`runs/打开QQ给王鑫说你好/trace.json` 及其 15 张截图。任务为打开 QQ，进入王鑫会话并发送“你好”。本次只分析已有运行记录和实现，不重跑模型、不操作手机、不修改运行代码。

后续进度（2026-10-05）：已实现建议第 1 项的思考控制、有界重试与请求诊断；随后加入按需重规划，修正 Verifier 的执行前图选择。188 项离线测试通过，正常 6 动作的模拟轨迹只调用 1 次 Planner、共 9 次模型请求。下面的数据与问题描述仍对应优化前的运行。[配置与流程说明](visual-agent.md)。角色上下文裁剪、记忆整理和编号轻量守卫等仍待处理，未重跑手机任务验证性能。

## 实测用量和时间

2026-10-06 分项实施：第 2 项已完成，角色上下文分别裁剪，记忆改为带稳定 key 的完整替换快照，190 项离线测试通过。后续设备守卫、输入聚焦和剩余日志工作仍待完成。

记录总耗时 139.219 秒，6 次设备动作、7 次决策、15 次逻辑模型请求，输入 177386 token，输出 12797 token。逻辑请求可能包含 HTTP 客户端内部的传输重试，trace 没有记录每个传输尝试。

| 角色 | 请求数 | 请求总耗时 | 输入 token | 输出 token |
| --- | ---: | ---: | ---: | ---: |
| Planner | 8 | 58.832 秒 | 92332 | 10974 |
| Executor | 6 | 10.123 秒 | 69384 | 1138 |
| Verifier | 1 | 3.901 秒 | 15670 | 685 |
| 合计 | 15 | 72.856 秒 | 177386 | 12797 |

剩余 66.363 秒不在逻辑模型请求计时内。通过请求开始时间、耗时和动作时间可以分解成以下区间；这些是区间总耗时，不是某条 ADB 命令的独立耗时。

| 非模型区间 | 总耗时 | 包含内容 |
| --- | ---: | --- |
| Planner 完成后到 Executor/Verifier 请求开始 | 21.435 秒 | 重新截图、图片处理、焦点和 A11Y 读取、记录及请求准备 |
| Executor 完成后到设备动作完成 | 26.930 秒 | 焦点检查、编号完整复读、点击/输入、输入法处理、动作间隔等 |
| 动作完成后重新观察 | 13.765 秒 | 截图、焦点和 A11Y 读取、图片处理、记录 |
| 其他 | 4.233 秒 | QQ 窗口变化后的额外观察、焦点检查、上下文准备、停止检查等 |

当前 config.yaml 的 action_interval 为 1 秒，按现有路径 6 次动作有约 6 秒固定等待，计入执行区间。trace 未保存当次配置副本，因此这不是独立计时实测值。初始观察在 Agent 循环计时开始前完成，不计入上述 139.219 秒。

## 主要问题

### 1. 每个动作都完整调用 Planner 和 Executor

6 次动作对应 6 对规划/执行请求，最后还调用一次 Planner 和一次 Verifier，加上一次修正请求，得到 15 次请求。三个角色默认同一个模型，却每轮都重复传全量上下文。正常打开会话、输入文字等动作也付出完整重新规划的代价。

第一步不是日志展示的 1283ms：Planner 从 0.342 秒到 4.359 秒，之后刷新页面到 10.737 秒，Executor 再花 1.283 秒，12.020 秒才得到点击决策；操作和再次观察后到 22.282 秒。

### 2. 一次思考耗尽输出预算，导致空正文和重新请求

第 3 个请求为 Planner：耗时 21.859 秒，输入 8188 token，completion_tokens=4095，其中 reasoning_tokens=4095。程序未得到可解析的 JSON 正文，报 `Expecting value`。第 4 个修正请求又花 8.256 秒，输出 1616 token。

请求统一设置 max_tokens=4096，未显式控制 thinking 或 reasoning_effort；也未记录 finish_reason。4095 个输出 token 全是思考，强烈符合思考消耗完预算、没有剩余预算输出 JSON 的情况，但因为没有 finish_reason，不能从 trace 最终确认截断原因。

全程 reasoning_tokens 合计 7006，占输出的 54.7%；那一次失败贡献其中 4095。它与此前的清单描述一致性错误不同，本次只有这一次 JSON 修正。

[DeepSeek 官方思考模式文档](https://api-docs.deepseek.com/guides/thinking_mode/)说明默认开启思考、默认强度 high，并提供控制参数。应针对实际服务的参数兼容性明确控制，不能只降低 max_tokens，否则可能更容易没有 JSON 输出。

### 3. 上下文没有按角色裁剪，记忆重复增长

`VisualAgent.context()` 给每个角色同一份原目标、全程动作摘要、最近 6 次详细动作、前后页面摘要、完整 progress、全部 installed_apps、当前 elements。Executor 只需落实一个子目标，却再次收到所有这些内容。

第一轮 Planner 输入 7168 token，最后 Planner 输入 15920 token，增长至 2.22 倍。用 trace 中的历史和原始角色输出重建状态后：

- 最后一次规划前有 17 条记忆；规划后累计 21 条。
- 最终 memory JSON 3322 字符，recent_outcomes JSON 11776 字符，progress JSON 4236 字符。
- 记忆按 fact 全文作为字典键合并。QQ 包名、桌面入口、王鑫会话、欢迎卡片等事实只要换个说法就会再次加入；过期的控件编号和位置也残留。
- 页面文字、动作参数和应用信息在多个字段里重复；历史 fingerprint、a11y_fingerprint、image_file 等审计字段也传给模型。
- installed_apps 不设数量上限、每个角色都收到；具体当次列表未保存，因此不能量化它的 token 占比。

这不是只需要把“最近 6 步”改成“最近 2 步”。应保留完整本地轨迹，但按角色发送必要信息，并把重复记忆整理成当前有效的事实。

### 4. 图片重复发送，但不能把 17.7 万输入全归因于图片

本次截图实际模型尺寸为 716×1600，原生尺寸为 1440×3216。按代码路径，前两个请求各一张图，之后 13 个请求各两张，共 28 次图片呈现，包括修正请求重复带图；没有显式设置 detail。

[DeepSeek 当前图像文档](https://api-docs.deepseek.com/guides/vision/)说明图像按尺寸转换为 token，单张最多 1024 token，auto 当前等同 original。若本次服务遵循这套当前规则，28 次图片最多 28672 token，不足以解释 177386 输入；文本上下文必须优先检查。trace 未分开统计图像和文字 token，也没有保留服务端点，因此不能给出本次精确分摊。

PNG 编码、base64 和传输体积会影响时间，但不能把 base64 字符数直接当作模型 token 数。桌面截图约 1.71MB，后续聊天页大多约 0.12–0.23MB。

### 5. 编号守卫重复执行完整视觉观察

本次有 15 次保存的完整观察，以及 5 次未保存的 fresh_index 完整观察，总计约 20 次。包含初始观察、每轮规划后刷新、执行后观察、焦点变化后观察、验证前刷新、编号动作执行前守卫。

`fresh_index()` 调用 `observe_visual()`，但最终只比较 app/activity/screen/a11y_fingerprint。因此为了检查编号表是否过期，又执行了 PNG 截图、缩放、网格叠加和编码。窗口守卫还另查一次焦点。

在 Portal 一次查询成功的典型路径中，单次 observe_visual 串行调用截图、焦点、Portal tree、焦点四个 ADB 往返。规划后和执行前校验具有正确性目的，不能直接全部删掉；编号守卫应改用只获取所需窗口、方向和 A11Y 表的轻量路径。当前 trace 缺少每个设备阶段耗时，无法把 66.363 秒进一步准确分成截图传输、Portal 查询、输入法、图片处理等。

### 6. 缓存和日志不能帮助判断实际成本

177386 个输入 token 中，服务端报告缓存命中 17152，未命中 160234，命中率 9.67%。其中 JSON 修正那次命中 8064，占全部命中很大部分，正常连续步骤的缓存效果较差。模型用量汇总正确包含各角色，缓存命中 token 仍计入输入总量，实际金额应按服务价格另算。

规划、修正、复核事件使用 state.elapsed_ms，常是上一张截图时间。例如日志的“0.0s 视觉规划”实际在约 4.359 秒后产生；25.3 秒的修正事件实际在失败请求结束约 47.208 秒时产生。动作决策行的 latency_ms 只代表 Executor，不能反映这一轮 Planner、页面读取和执行的总耗时。

## 一并发现的验证问题

`VisualAgent.decide()` 在进入 Verifier 前把 previous_page 改成当前完成提议页面，再拍新图。这次 Verifier 实际拿到 `128526-014.png` 和 `135089-015.png`，两张均已显示“你好”发送气泡和空输入框。32×32 灰度平均差异只有约 0.00586，肉眼核对也确认是同一发送后状态。

Verifier 声称“上一张是发送前”不符合实际图片。历史里确实有输入和发送操作，当前结果也支持成功，但图像前后变化的证据表述错误。应保留最后一个动作的真正执行前截图，再与新采集的完成图比较。

## 建议调整顺序

1. 明确控制模型思考强度，Executor 优先关闭不必要的思考；记录 finish_reason、reasoning_tokens 和空正文原因，避免同配置盲重试。具体参数按服务能力使用。
2. 按角色组织输入：Executor 使用原任务约束、子目标、当前控件和截图、最近结果及必要反馈；Planner 使用累计进度与精简历史；Verifier 使用原要求、关键完成证据、真正执行前/当前图片。完整记录留在本地。
3. 把 memory 改为维护当前事实，停止按全文累积同义改写；审计字段不默认传入模型，应用包清单仅在需要启动 App 的上下文中提供。
4. 将 fresh_index 改为轻量校验，保留编号过期保护；对观察阶段加分项计时，测清 ADB 和图片处理开销后再决定并发采集或刷新策略。
5. 避免为了输入框聚焦额外用一整轮模型：TYPE_TEXT 已能按 index 点击目标并输入。保持“一次只执行一个设备动作”的契约，不将发送和输入盲目批量执行。
6. 在上述可测浪费消除后，再考虑让 Planner 只在需要新规划、失败、明显状态变化和完成提议时调用，由 Executor 连续落实当前计划；需要额外验证持续计划的正确性。
7. 修正事件时间戳和日志耗时含义、保留配置与请求体积/图片数量等元数据，同时修正 Verifier 的前图选择。

没有对优化后的总耗时或 token 节省比例作承诺；需实施后对同类任务测量。为避免重复发消息，本次没有重跑 QQ 任务。
